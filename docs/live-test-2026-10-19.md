## Result

Live raw/compressed streaming is confirmed for the tested **iM3B-C**. It is
**not confirmed for iM3-C**: that device was offline in the account status snapshot
and its initial registration returned an HTTP-like 404 before any media arrived.
That failure is not a finding of model incompatibility.

## Method

- Runtime: CPython 3.12.15, macOS ARM64, local `mibo-py` checkout. SDK source
  corresponds to commit `b3168cc`.
- The owner explicitly authorized testing these two account devices. Stored
  selectors were bound to the same account and fresh inventory model before open;
  other inventory devices were not opened.
- The package's signed HTTP implementation revalidated an existing authorized
  token with `Login`. Returned account user ID and route were checked against
  that caller-held session before constructing the package account session.
  This used the existing low-level HTTP/session interfaces, not a new public
  session-restore API. A separate password attempt returned a 2FA challenge;
  no code was requested or bypassed.
- Camera details and bootstrap were fetched fresh through the Python package.
  Profile subtype 1 was selected explicitly. No vendor application, proprietary
  SDK, .NET transport, or native camera runtime supplied the test stream.
- One open consumed original DHAV records, checking the SDK framing, lengths
  and checksum. A second open consumed the SDK's decrypted H.264 Annex B and
  AAC ADTS units for 75 seconds, crossing the normal method-2 keepalive intervals
  without automatic reconnection.
- A bounded H.264 prefix stayed in memory and was piped to a separate `ffprobe`
  process to inspect codec/dimensions. No frame image, PCM output or media file
  was produced. This is an independent validator, not a runtime dependency of
  `mibo-py` or proof of decoded/presented frames.
- Each stream was explicitly closed; socket descriptors were checked closed.
  Method-3/DISC remains best-effort. Local cleanup does not prove remote
  resource reclamation.
- A diagnostic attempt on iM3-C read its current offline status and observed
  404 at initial NFPOST registration. No arbitrary shard or LAN destination
  was contacted to work around the rejection.

## Correction discovered by live testing

The service returned an approved account origin with explicit HTTPS port 443.
The earlier exact-string origin policy rejected that otherwise permitted form.
The fix accepts only `https://<existing-approved-host>:443` with an empty or root
path, retains the same two-host allowlist, and adds synthetic regressions for
both hosts. Alternate ports, userinfo, paths, queries and fragments stay rejected.

The previous README also associated historical LAN playback with iM3-C. The
stored inventory shows that playback camera was another iM3B-C. That assertion
has been corrected; inventory visibility is not media acceptance.

## Limits

This establishes only the observed account, firmware, public network path,
profile and macOS ARM64 Python implementation. It does not establish iM3-C
streaming, LAN or relay operation, other profiles/firmware/platforms, audible
playback, perceptual synchronization, lossless delivery, arbitrary duration,
fresh password/2FA acceptance, or server-side close confirmation. An online
iM3-C run is still required. No camera/account settings were changed and no
media was saved or played. CI remains fully offline with respect to cameras.
